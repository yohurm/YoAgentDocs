# 验收标准与结束语义

验收条目是本轮工作的合同：每条只能 **通过** 或 **未通过**。类型包质量门禁是每轮都要满足的共性底线。两边全部通过，才允许写完成总结、才允许结束对话。做了 90% 仍是未完成。

写条目时不要写日期、deadline、排期；那不是验收，是项目管理。

## 必须：怎么写一条验收

一条验收必须同时满足：

- **可观察：** 写清用什么证据判定（界面状态、文件内容、命令输出、日志、接口响应、截图）。写不出证据的句子删掉。
- **可二判：** 两个人看同一证据会得出同一结论。做不到就改写到能做到。
- **一条一事：** 一条只钉一个行为或一个边界。一条里混三件事，拆开。
- **有前置与结果：** 优先 Given / When / Then（给定状态 → 动作 → 可观察结果）。规则型清单也可以，但每条仍须能单独判过/不过。
- **含失败路径：** 不只写主路径。空态、错误输入、权限不足、中断恢复等，任务涉及的都要有条。
- **判结果不判实现：** 写「用户看到什么 / 系统留下什么」，不写「必须用某某类名」。

开工前把本轮验收列成清单：用户已给的用原话改写成可判定句；用户没给的，从任务目标 + 类型包门禁推出，并在动手前亮出来。清单未齐，不算开始收尾。

## 禁止写进验收

| 禁止 | 原因 | 改成 |
|------|------|------|
| 更好、完善、合理、流畅、体验好、专业 | 无法判定 | 具体状态、文案、数值、文件 |
| 尽快、本周、某日上线、在 deadline 前 | 日期不是行为是否正确 | 删掉；行为对错与日历无关 |
| 基本完成、大致可用、完成度 90% | 中间态 | 拆成多条，每条过或不过 |
| 尽量、适当、必要时 | 谁都可以说自己做到了 | 写触发条件与必须结果 |
| 代码质量高、架构清晰 | 空话 | 落到本库已有规则（分层、无兼容层、无越级）的可检查项 |

## 必须：结束语义

实现新功能、修复缺陷、按分层改代码时：

1. 列出本轮全部验收条目（任务条目 + 类型包门禁）。一条都不能少。
2. 逐条给 **通过 / 未通过** 和证据。禁止打分、禁止「大部分过了」。
3. **任一未通过 → 不得总结、不得结束对话。** 回到该条相关的完整数据链路（入口 → 状态 → 变换 → 副作用）继续查、修、再验同一条。
4. **全部通过 → 才允许** 写根因/改动/证据并结束本轮。
5. 环境做不到某条验证：写明缺口，该条记未通过，本轮仍未完成。能继续推进的实现与修复不得停。

表面符合但实质未完成（文件有了但是空的、测试绿了但没覆盖该行为、UI 挡住了错误）记 **未通过**。

## 反例

- 「功能已完成，还差空态和禁用，用户可以先看。」→ 空态、禁用若在清单里，整轮未完成。
- 「主流程过了，边界明天再补。」→ 验收里没有明天。
- 「完成度大约九成，先总结。」→ 禁止。
