# 修改已有代码

先判断任务属于哪一种，再选改法。不要把「重做整个仓库」和「修一处行为」混用。拟议改动若是在旧分层上打补丁、叠兼容或做防御性加固：按模块重设计处理，不要走行为修复。

## 行为修复（默认）

- 先读调用方、边界和已有验证，再改。
- 只改完成任务所需的模块与行；禁止无关重排、无关重命名、整文件格式化。
- 根因在哪一层就改哪一层，避免在调用处叠一层掩盖。禁止空判断/吞异常/延时重试/只改 UI 当修复；禁止为「保险」加无依据分支。细则见 [architecture.md](../common/architecture.md)「旧架构不打补丁」「禁止防御性修补」。
- 注释遵守 [development.md](../common/development.md)：只保留代码自身应有的必要注释，严禁掺入「章节实现」、「任务步骤」等过程性标记。
- 保持未声明变更的对外契约（API、CLI、文件格式、环境变量）。
- 风格跟周围代码走。

## 模块重设计（用户要求架构/分层/重做该模块，或拟议改动会落成打补丁/加固时）

- 先严格调研已验证的优秀设计（官方规范 + 开源实现，见 [design-sources.md](../common/design-sources.md)），再重画该模块完整数据链路。没有出处与链路证据不得开改，严禁猜测。
- 以该模块的目标分层为准。发现兼容性代码或兼容层：沿全部相关数据链路查根因，重设计完整通路；去掉双轨 API 和过渡适配，不要再留一层「兼容」。
- 把问题重构到新通路上，并删除旧实现；不要注释冻结。
- 仍然只动这个模块及其必要调用点，不借机重写无关模块。
- 重设计必须带上数据链路：改前调用链 + 改后通路证据（见 [architecture.md](../common/architecture.md)）。
- 重设计前用几句话说明新边界和影响面；用户已把任务定义成重设计，或拟议改动本身就是打补丁/加固时，不必再等二次批准。

## 共性

- 行为变化按类型包做验证。
- 纯重构不得改变行为；不能保证就不要在行为修复任务里夹带重构。
- 与任务无关的脏代码可以记下来，不要顺手清理。
